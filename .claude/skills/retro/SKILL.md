# /retro [日数] — ループの振り返りと書き戻し

考え方: エージェントがミスしたら、出力を直すのではなく、**二度と同じミスが起きないように環境を直す**（Mitchell Hashimoto の harness engineering、Boris Cherny / Every の compounding engineering）。ただし、いきなり「問題を探して」と丸投げしない。実データを文脈ごと読み、分類し、数え、判断に迷うものは人に確かめる（Hamel Husain の error analysis）。

引数: 振り返る日数（既定 14）。

## 1. 材料を集める（読むだけ）
1. `node scripts/retro-signals.mjs --days <N>` — このリポジトリ（main と worktree）のセッション記録から、人が打ったメッセージを **直前にエージェントが言ったこと・していたこと（`agent:`）と一緒に** 抜き出す。付いているのは事実だけで、意味の判定はしていない:
   - `mid-turn`: エージェントの作業中に送られた
   - `after-interrupt` / `after-rejected-tool` / `after-hook-block`: 直前に、人が作業を止めた / ツール実行を拒否した / hook が止めた
   - `restates#N`: 同じセッションの N 番目のメッセージと内容が重なっている
2. 直近にマージされた PR の、人間のレビューコメント:
   ```bash
   gh pr list --state merged --search "merged:>=$(date -d "-<N> days" +%F)" --json number,title
   gh api repos/hackdays-io/toban/pulls/<n>/comments --jq '.[] | select(.user.type=="User") | {path, body}'
   ```
3. 個人メモリに「この人の言い方の傾向」（過去の `/retro` で確認したもの）があれば先に読む。
4. それでも判断できない箇所は、該当セッションの JSONL（`~/.claude/projects/<repo を - でつないだ名前>*/<session>.jsonl`）の前後を読む。

## 2. 1 件ずつ、文脈で判断する（open coding）
各メッセージを `agent:` と並べて読み、次のどれかを判断する。**単語では判断しない**:
- **了承・指示・質問**（摩擦ではない）: 「含めて」「うん」のように、エージェントの問いへの返事や、新しい依頼。
- **ズレの修正**: エージェントの作業・報告と違う方向を示している（言い方が穏やかでも該当する）。
- **言い直し**: 前に言ったことが伝わっていない、または実装に反映されていない。
- **説明の要求**: エージェントが作った物・言った事が理解されていない（報告が足りない、または長すぎる）。
- **割り込み・拒否**: 作業中に送った、止めた、拒否した。何に対してかを `agent:`（`then:` のツール）から特定する。

**その人の普段の言い方を基準にする**。期間内の全メッセージを一通り読み、多くのセッションに出てくる言い回し・文体（短い返事、「とりあえず」等）は口癖として扱い、それだけを根拠に摩擦とはしない。判断の根拠はいつも「直前の文脈に対してどう反応したか」に置く。

出来事は事実だけを 1 行で書く: 「エージェントが X と報告 / X をしていた → 人が Y と返した」。原因の推測はまだしない。

## 3. 迷うものを人に確かめる
摩擦かどうか自信が持てない出来事を **最大 5 件** まで選び、`AskUserQuestion` でユーザーに聞く（例: 「『表にしないで』は、ターミナルで読みにくいからですか、それとも内容が表に向かなかったからですか？」）。
- 答えから分かった **その人の言い方の傾向や好み** は、ユーザーの了承を得て個人メモリに保存する（次回以降の基準になる）。リポジトリには入れない。
- 定期実行などで人がいない場合は聞かずに、迷うものを「保留」として PR 本文に列挙する。

## 4. まとめて数える（axial coding）
似た出来事をまとめ、種類ごとに件数を出す。種類の例:
- 依頼の誤解・前提の取り違え
- 拡張や将来の変更を考えていない設計
- 報告・説明が足りない、長すぎる、形式が合わない
- 毎回口頭で指示している手順（**セッションをまたいで** 同じ指示が出ていないかを必ず見る。スキル化・自動化の候補として最も価値が高い）
- 仕組み（hook / verify）の誤検知・過剰なブロック
- 層をまたぐ同期漏れ・デプロイ順序のミス

**1 回きりのものは保留**（偶然かもしれない）。2 回以上か、1 回でも重大なもの（本番への影響、データ損失、秘密情報）だけを次に進める。

## 5. 反映先を決める（強制力が強い順に検討する）
| 反映先 | 向いているもの |
| --- | --- |
| hook（`.claude/hooks/`、`.claude/settings.json`） | 絶対に守るべき禁止事項・手順 |
| `scripts/verify.sh` / テスト / 各パッケージの `verify` スクリプト | 機械的に判定できるミス |
| スキル（`.claude/skills/`）・`toban-reviewer` | 毎回の手順、レビューの観点 |
| `AGENTS.md`（ルートか各パッケージ） | 判断の基準・規約・前提知識。1 項目 1〜2 行、看板のように短く |
| 個人メモリ（`~/.claude/` 側） | その人だけの好みや言い方の傾向。リポジトリには入れない |

各改善案には、根拠となった出来事（日付、セッション ID の先頭 8 文字、要約）を付ける。根拠を示せない案は出さない。

## 6. 削る
`AGENTS.md`・スキル・reviewer の項目のうち、根拠が見当たらないもの、仕組みで強制済みになって文章が要らなくなったものを削除候補に挙げる。ファイルを短く保つことも改善のうち。

## 7. 出す
- リポジトリに入れる変更は worktree で作り、`scripts/verify.sh` を通してから **PR にする**。自動では反映しない。PR 本文には次を書く:
  - 振り返った期間、見たセッション数と PR 数
  - 種類ごとの件数の表
  - 改善案ごとに「根拠 → 変更内容 → 期待する効果」
  - 削除した項目とその理由
  - 保留したもの（1 回きりの出来事、人に確認できなかったもの）
- **会話の原文をそのまま PR に貼らない**。要約し、個人名や秘密情報は入れない。
- 最後に、ユーザーへ 5 行以内で報告する: 見つけた主な摩擦、入れた改善、個人メモリに保存したこと、保留したもの。

## 定期実行
週 1 回の振り返りは `/schedule` で設定できる（例: 毎週月曜に `/retro 7`）。あわせて、`/ship` の最後でその PR 単位の小さな書き戻し（compound）も行う。
